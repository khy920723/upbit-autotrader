# 불변식 명세

상태: 초안 · 2026-11-05 · 관련: [테스트 전략](test-strategy.md), [추적표](traceability.md), [가짜 구현 명세](fakes-spec.md), [위험 관리 정책서](../03-functional/risk-policy.md), [상태 전이 정의서](../03-functional/state-machines.md), [매매 로직 명세](../03-functional/trading-logic.md)

어떤 입력, 어떤 장애, 어떤 순서에서도 깨지면 안 되는 성질(불변식, INV-)과 그것을 증명하는 테스트를 정한다. 테스트 전략 1장의 "위험 한도를 넘는 주문이 나가지 않는다는 것이 가장 중요한 성질이다"를 검사할 수 있는 문장으로 바꾼 것이다.

## 1. 용어

| 용어 | 뜻 |
|---|---|
| 주문 | 주문 생성 요청. 업비트 `POST /v1/orders`, `POST /v1/orders/test`, 그리고 paper의 가상 거래소 주문 접수. 취소 요청(`DELETE`)은 주문이 아니다 |
| 만든다 | identifier를 만들어 CREATED로 저장하는 것 |
| 보낸다 | 브로커가 요청을 내보내는 것. 만든 시점과 보내는 시점 사이에 상태가 바뀔 수 있다 |
| 끝나지 않은 주문 | CREATED, SUBMITTED, OPEN, PARTIAL, UNKNOWN |
| 노출 | 보유 평가금액 + 미체결 매수 금액([용어 정의서](../01-planning/glossary.md)) |
| 기준 구현(오라클) | 정책서의 식을 그대로 옮긴 테스트 쪽 판정 코드. 프로덕션 코드를 import하지 않는다 |

## 2. 공통 증명 방법

### 2.1 테스트 종류

| 종류 | 쓰는 곳 | 도구 |
|---|---|---|
| 단위 | 계산·판정 함수의 경계값, 표 기반 검사(상태 × 동작 등) | pytest |
| 속성 기반 | 임의 입력에 대한 성질(hypothesis `@given`), 임의 사건 순서에 대한 성질(hypothesis 상태 기계 `RuleBasedStateMachine`) | hypothesis |
| 통합 | 실제 core + 가짜 구현(FakeExchange, FakeClock 등)으로 끝에서 끝까지 | pytest + [가짜 구현](fakes-spec.md) |
| 구조 검사 | 코드에 금지된 호출·경로가 없는지(AST) | pytest. `tests/unit/test_architecture.py`(2단계)와 같은 방식 |

### 2.2 hypothesis 사용 규칙

- **의존성:** hypothesis는 아직 dev 그룹에 없다(2026-11-05 main의 `pyproject.toml` 기준). 인프라 세션이 dev 그룹에 추가하고, 기획 세션이 CLAUDE.md "고정 기술 기준"의 dev 그룹 목록을 고친다. 2026-11-05 PyPI 최신은 6.170.14(2026-10-30, Python 3.11 이상).
- **예제 DB:** hypothesis는 실패 예를 `.hypothesis/` 폴더에 저장한다. `.gitignore`에 추가한다(인프라 세션).
- **프로필:** `dev`(빠름)와 `ci`(많은 예, `deadline=None`, `print_blob=True`)를 `conftest.py`에서 등록하고 환경 변수로 고른다. 비동기·Qt 테스트는 시간 편차가 커서 `deadline=None`을 쓴다.
- **재현:** 한 번 찾은 반례는 `@example(...)`로 테스트에 고정해 회귀를 막는다.
- **독립 오라클:** 위험 한도 검사(INV-01) 같은 성질은 프로덕션 함수의 결과를 같은 함수로 확인하면 의미가 없다. 테스트 쪽에 정책서 식을 그대로 옮긴 짧은 기준 구현을 두고 비교한다.
- **공허한 통과 막기:** 안전 불변식(INV-01~06)은 주문을 하나도 내지 않으면 저절로 지켜진다. 상태 기계 테스트는 (1) 주문이 실제로 나간 예의 비율을 `hypothesis.event()`로 남겨 `--hypothesis-show-statistics` 출력으로 확인하고, (2) 조건이 모두 맞으면 주문이 실제로 나가는지(활성 성질. 손절은 INV-09, 매수도 같은 방식)를 함께 검사한다.
- **상태 기계 규칙(공통 사건):** 시그널 도착, 가격 변동, 체결·부분 체결, 타임아웃(보내기 전·접수 뒤), 5xx·429·418, 재시작(아무 지점에서 프로세스 종료), 설정 변경(완화·강화), 시간 경과(09:00 경계 포함), 일시정지·재개·정지·정지 후 전량 매도·시작, 모드 전환 시도, 잠자기 복귀. core는 FakeClock으로 한 단계씩 돌릴 수 있어야 한다(구현 세션에 요청).
- **느린 테스트:** 상태 기계와 장시간 테스트는 마커(예: `slow`)를 붙인다. pytest 설정이 `--strict-markers`라서 마커를 `pyproject.toml`에 먼저 등록해야 한다.

### 2.3 실행 중 검사

- 테스트와 별도로, 브로커가 주문을 보내기 직전에 INV-01·02·05·06을 한 번 더 확인한다. 깨지면 보내지 않고 `InvariantViolation`으로 HALTED로 간다(시스템 구성도 7장 오류 타입 표, 모든 모드, D-058). 이 확인 코드 자체도 단위 테스트한다.

## 3. 불변식

### INV-01 위험 한도를 넘는 주문 0건

- **정의:** 매수 주문 o를 만든 시점의 상태에서 아래가 모두 참이다.
  1. 매매 상태가 RUNNING이다.
  2. o의 금액 ≤ 내림(min(코인별 예산 − 코인 노출, 전체 노출 상한 − 전체 노출, 주문 가능 원화) ÷ (1 + `bid_fee`)). 분할 매수면 회차 금액 이하([매매 로직 명세](../03-functional/trading-logic.md) 7장).
  3. `min_total` ≤ o의 금액 ≤ `max_total`(`/v1/orders/chance` 값. 매수는 `market.bid.min_total`, D-067. 키 없는 paper는 공식 문서 추정값, D-059 대기). 첫 매수(포지션 FLAT)면 o의 금액 ≥ 예산 하한(매도 `min_total`과 손절%로 계산, RISK_BELOW_FLOOR, D-067, TS-84).
  4. 그날(09:00 KST 기준) 실현 손실 합계(손실이 난 매도 체결만 더하고 이익과 상계하지 않음, D-056)가 일일 손실 한도에 닿지 않았다.
  5. 그날 주문 수 < 일일 주문 수 상한.
  6. 같은 코인에서 거래소가 접수한 직전 주문 뒤로 최소 주문 간격이 지났다(접수되지 않은 429·418·4xx 거절은 세지 않음, D-061 대기).
  7. 경고 종목이 아니고 재진입 제한 중이 아니다.
  8. 그 코인에 끝나지 않은 주문이 없다(INV-04).
  9. 시그널이 positive이고 확신도 ≥ 임계값이며 규칙 조건을 만족한다.
- 매도 주문은 수량 ≤ 보유 수량(live는 거래소 기준)이고 금액 ≥ `min_total`이다. 미만이면 주문하지 않고 잔량으로 기록한다.
- **깨지는 예:** 미체결 매수를 노출에서 빼먹음. 두 코인을 동시에 평가하면서 전체 노출을 따로 계산해 합이 넘음. 수수료를 빼지 않아 주문 가능 원화를 넘음. 손절 체결 직후 일일 손실이 반영되기 전에 매수. 완화한 설정을 확인 전에 씀.
- **증명:**
  - 단위: 조건마다 경계값(−1, 0, +1원·초·건) 표.
  - 속성: 임의 위험 문맥(한도, 노출, 잔고, 수수료, 주문 수, 손익, 상태, 시각)으로 `approve_buy` → 승인이면 기준 구현이 1~9를 모두 참으로 판정하고, 거부면 이유 코드가 실제로 거짓인 조건 중 하나다. 한도를 엄격하게 바꾸면 승인 금액이 늘지 않는다(단조성).
  - 통합(상태 기계): FakeExchange가 주문을 받을 때마다 그 순간의 가짜 거래소 상태와 앱 설정으로 기준 구현을 돌린다. 어기면 `FakeProtocolViolation`.
- **관련:** TS-11, TS-29, TS-31, TS-36, TS-60, TS-81, TS-84, TS-113, TS-114 · 5단계

### INV-02 STOPPED·SUSPENDED·HALTED에서 주문 0건

- **정의:** 매매 상태가 STOPPED, SUSPENDED, HALTED인 동안 주문을 만들지 않는다. 보내기 직전에 상태를 다시 확인해 이 상태면 보내지 않는다. 함께 지키는 표([상태 전이 정의서](../03-functional/state-machines.md) 2장): PAUSED·BUY_BLOCKED·DEGRADED·LIQUIDATING에서 신규 매수 0건, LIQUIDATING에서는 전량 매도만.
- 정지로 들어갈 때의 미체결 취소는 주문이 아니다. 상태가 바뀌기 전에 이미 보낸 주문은 결과 확인만 한다. paper도 같다(가상 거래소 주문 0건).
- 내부 오류(불변식 위반, 위험 점검·주문 관리 예외 3회 연속)도 모든 모드에서 HALTED로 가므로 이 불변식이 적용된다(D-058, TS-83).
- [정지]·[정지 후 전량 매도]를 확인하면 취소·매도보다 먼저 STOPPED를 저장한다. LIQUIDATING 중에 꺼지면 STOPPED로 다시 시작하고 전량 매도를 자동으로 이어 하지 않는다(D-069, TS-86).
- **깨지는 예:** 손절 점검이 상태를 확인한 뒤 [정지]가 들어오고 그대로 주문이 나감(확인과 전송 사이 경쟁). 재시작 복원에서 STOPPED를 RUNNING으로 잘못 복원. HALTED인데 다른 코인 주문은 나감.
- **증명:**
  - 단위: 상태 8개 × 동작 4개(신규 매수, 손절·청산 매도, 시그널 평가, 전량 매도) 표 전체.
  - 속성(상태 기계): 상태가 이 셋 중 하나인 구간에 FakeExchange가 받은 주문 수 = 0을 `@invariant()`로 검사. "점검 시작 → 정지 → 전송 직전"처럼 끼어드는 순서를 규칙으로 만든다.
  - 통합: 정지(TS-32), 418(TS-05), 허용 IP 오류(TS-06), 내부 오류(TS-83) 시나리오의 FakeExchange 기록.
- **관련:** TS-05, TS-06, TS-24, TS-32, TS-83, TS-86, TS-87, TS-123 · 5·7단계

### INV-03 같은 identifier로 다시 보내지 않음

- **정의:** (1) 모든 identifier는 주문 API로 최대 한 번 나간다. 재시도, 재시작, 크래시, 재조정 어떤 경우에도. (2) 나가는 주문의 identifier는 보내기 전에 DB에 커밋되어 있다. (3) identifier는 64자 이하이고 앱의 모든 이력에서 겹치지 않는다.
- 업비트가 `duplicated_identifier`를 돌려주면 같은 요청이 한 번 더 전달돼 주문이 이미 있을 수 있으므로, REJECTED로 닫지 않고 UNKNOWN으로 두어 조회로 확정한다(D-070, TS-89).
- **깨지는 예:** HTTP 클라이언트·SDK의 자동 재시도가 POST를 다시 보냄. 타임아웃을 "실패"로 보고 같은 주문 객체를 다시 보냄. 재시작 때 CREATED를 "아직 안 보냄"으로 보고 다시 보냄. DB 커밋 전에 전송(그 사이 크래시하면 거래소에만 주문이 남음). 시각 기반 identifier가 같은 초에 겹침.
- **증명:**
  - 단위(속성): 생성한 identifier의 형식과 길이(64자 이하, 앱 접두어, 공백·`+` 없음). D-047 형식은 임의 부분이 16진수 8자(32비트)라 같은 초에 많이 만들면 겹칠 수 있으므로, 대량 생성으로 "겹침 0"을 시험하지 않는다. 대신 가짜 난수로 같은 값을 일부러 두 번 내게 해도 DB 고유 제약에 걸려 새 값을 만들고, 겹친 identifier는 저장·전송되지 않는지 본다.
  - 속성(상태 기계 + 크래시 주입): "아무 지점에서 프로세스 종료"(CREATED 커밋 직후, SUBMITTED 커밋 직후, 전송 중, 응답을 받고 커밋하기 전)를 규칙으로 넣고 같은 DB로 다시 시작. `FakeExchange.orders_received(id) ≤ 1`이고, 받은 순간 그 identifier가 DB에 있었다(DB 조회 콜백).
  - 통합: TS-01(타임아웃), TS-66(5xx), TS-68(재시작).
- **관련:** TS-01, TS-66, TS-68, TS-89, TS-117 · 3단계(클라이언트 재시도 끔), 5단계

### INV-04 결과 불명 중 같은 코인 새 주문 없음

- **정의:** 코인에 결과 불명(UNKNOWN) 주문이 있는 동안 그 코인의 새 주문을 만들지 않는다. 손절도 마찬가지다. 다른 코인은 영향이 없다. 매매 로직 명세 4장은 이 범위를 끝나지 않은 주문 전체로 넓혔다. UNKNOWN 절차는 live의 실제 주문에만 쓰고, live-validate·paper는 재시작 때 남은 주문을 REJECTED(VALIDATE_TIMEOUT, PAPER_RESTART)로 닫는다(상태 전이 정의서 3장). UNKNOWN은 정해진 확인 절차(D-046: 조회 일정, "없음" 3회 이상, 60초 경과, 목록 조회)를 마쳐야만 REJECTED가 되고, 네트워크 실패만 이어졌으면 REJECTED가 되지 않는다.
- **깨지는 예:** 손절 점검이 UNKNOWN을 무시하고 새 손절 주문을 내 이중 매도. 60초 타이머만 보고 REJECTED로 확정. 늦게 나타난 주문을 반영하지 않음. 한 코인의 UNKNOWN 때문에 다른 코인의 손절까지 멈춤(INV-09 위반).
- **증명:**
  - 속성(상태 기계): `timeout_after_accept`, `not_found_for`, `lookup_error`를 섞는다. 코인별 끝나지 않은 주문 ≤ 1. REJECTED(NOT_FOUND_AFTER_UNKNOWN)로 확정된 주문에는 "없음" 3회 이상과 60초 경과 기록이 있다.
  - 통합(가짜 시계): TS-02, TS-67, 5분 뒤 NTF-16.
- **관련:** TS-02, TS-67, TS-68 · 5단계

### INV-05 같은 코인에 매수·매도 동시 주문 없음

- **정의:** 어느 순간에도 한 코인의 거래소 미체결 주문 중 앱 주문(`uat-` 접두어)은 한 건 이하이고, 매수와 매도가 함께 열려 있지 않다. 코인별로 주문을 하나씩만 만들도록 직렬화(잠금)해서 지킨다(D-070, TS-92). 같은 코인에 사용자 수동 주문이 있으면 앱이 막을 수는 없으므로 경고 이벤트로 남긴다.
- **깨지는 예:** 매수 주문의 응답을 기다리는 동안 손절 점검이 매도를 냄. 부분 체결된 매수가 남아 있는데 매도.
- **증명:** 단위 TS-14. 속성(상태 기계): `FakeExchange.open_orders(market)`를 `@invariant()`로 검사.
- **관련:** TS-14, TS-69, TS-92 · 5단계

### INV-06 모든 주문에 smp_type

- **정의:** 주문 생성·검증 요청 본문에 `smp_type`이 있다. 값은 `cancel_maker`다(D-047, 유효(초안)). `post_only`는 쓰지 않는다. paper·live-validate 기록에도 같은 값이 남는다.
- **깨지는 예:** 새 주문 종류(예: 선택 해제 매도)를 추가하면서 빼먹음. 2026-11-09 이후 서버 기본값에 기대어 생략.
- **증명:** 단위(요청 만드는 함수: 주문 종류 × 모드 전체), 속성(임의 주문 요청 → 직렬화한 본문에 `smp_type`), FakeExchange 엄격 모드(모든 통합 테스트에서 자동).
- **관련:** TS-13 · 3·5단계

### INV-07 비밀이 로그·DB·프롬프트·알림·파일에 없음

- **정의:** 업비트 Access·Secret Key, JWT와 `Authorization` 헤더 값, Gemini 키, 네이버 Client Secret, 텔레그램 토큰(과 그것이 든 URL)은 keyring 밖 어디에도 남지 않는다. 대상: 로그, DB의 모든 테이블, 설정 파일과 백업, CSV, 진단 묶음, self-test 보고서, LLM 프롬프트, 텔레그램 메시지, 예외 메시지와 traceback. 화면에는 앞 4자리만 보인다. 계정 정보와 잔고 총액은 알림과 프롬프트에 없다.
- **깨지는 예:** HTTP 예외 메시지에 텔레그램 URL(토큰 포함)이 들어가 로그에 남음. 요청 헤더 전체를 DEBUG 로그로 남김. `order_events.payload_json`에 요청 헤더를 저장. 설정 객체 전체를 직렬화해 저장. LLM 입력에 잔고를 넣는 변경.
- **증명:**
  - 단위(속성): 가리기 필터에 임의 비밀(정규식 특수 문자 포함)과 임의 로그 메시지(비밀을 앞·뒤·중간에, `%` 인자·`extra`·예외로)를 넣어도 출력에 비밀이 없다.
  - 통합: 카나리아([가짜 구현 명세](fakes-spec.md) 7장). 마법사 → 주문 → 오류 경로 → 알림 → CSV → 진단 묶음을 지난 뒤 모든 출력에서 카나리아 0건.
  - 저장소: [PR 검토 기준](review-checklist.md)의 비밀 검사.
- **관련:** TS-46, TS-57, TS-100, TS-127, TS-140 · 2단계(로그)부터 모든 단계

### INV-08 위험 검사를 건너뛰는 경로 없음

- **정의:** 브로커에 들어가는 주문은 모두 위험 관리가 만든 승인 객체다. 위험 검사를 끄거나 줄이는 설정, 환경 변수, 명령줄 인자, 디버그 플래그가 없다. LLM 출력은 주문 금액과 손절에 영향을 주지 않는다.
- **깨지는 예:** 테스트 편의로 `skip_risk` 인자를 추가. 전량 매도 경로가 위험 관리를 거치지 않고 브로커를 직접 부름. 환경 변수 하나가 한도를 끔.
- **증명:**
  - 구조 검사(AST): 승인 객체 생성자를 부르는 곳이 위험 관리 모듈뿐이다. core·app에서 `os.environ`·`sys.argv`를 읽는 곳의 목록을 고정해, 새로 생기면 테스트가 실패하고 검토 뒤 목록에 추가한다. 설정 스키마에 위험 검사를 끄는 키가 없다.
  - 속성(변형 관계): 같은 위험 문맥에서 LLM 확신도(임계값 이상 범위)와 이유를 바꿔도 승인 금액이 같다.
- **관련:** TS-115 · 5단계

### INV-09 손절은 실제로 나간다 (활성 성질)

- **정의:** 매매 상태가 RUNNING, PAUSED, BUY_BLOCKED, DEGRADED이고, 보유 코인의 평가손실률이 손절선에 닿았고, 그 코인에 끝나지 않은 주문이 없으면, 다음 위험 점검(JOB-02, 60초 이내)에 매도 주문을 만든다. 일일 주문 수 상한, 일일 손실 한도, 다른 코인의 결과 불명은 이것을 막지 않는다. 손절 주문이 429로 거절되면 최소 주문 간격을 기다리지 않고 다음 초에 새 identifier로 다시 보낸다(D-061 대기, TS-82). 시작 점검(CHECKING) 중에는 대조가 끝날 때까지 손절 주문을 내지 않고, 상태가 정해지면 바로 손절을 점검한다(D-070, TS-97). 접수된 주문 뒤 60초 안의 손절에 간격을 적용하는지는 결정 필요([추적표](traceability.md) Q-01). 내부 오류로 HALTED가 되면 손절도 멈춘다(D-058). 매도 금액이 `min_total` 미만이면 주문하지 않고 잔량으로 기록한다.
- 안전 불변식(INV-01~06)은 아무것도 하지 않아도 지켜지므로, 이 성질을 함께 증명해야 한다.
- **깨지는 예:** 일일 주문 수 상한이 손절까지 막음. DEGRADED에서 웹소켓 가격을 기다리느라 손절하지 않음. 다른 코인의 UNKNOWN이 모든 주문을 막음. 손절 주문이 429를 받은 뒤 재시도가 다음 주기로 밀림(정책은 다음 초).
- **증명:**
  - 속성(상태 기계): 조건을 만족한 시각부터 FakeClock 60초 안에 매도 주문이 FakeExchange에 도착하거나, 기록된 정당한 이유(금액 미만, 끝나지 않은 주문)가 있다.
  - 통합: TS-27, TS-28, TS-31, TS-04, TS-82.
- **관련:** TS-04, TS-17, TS-27, TS-28, TS-31, TS-82, TS-97 · 5단계

### INV-10 실제 보유분을 관리 없이 두지 않음

- **정의:** live → paper 전환 같은 모드 전환이 앱이 관리하던 실제 보유분(선택 코인의 live 포지션)을 손절·청산 점검 대상에서 조용히 빼지 않는다(D-035). MSG-C008의 세 선택지 어느 것을 골라도 그 보유분은 "매도됨", "exit_only로 관리 중", "전환 취소" 중 하나다. exit_only 실보유분이 있으면 paper에서도 실자산 감시(비공개 웹소켓, JOB-05, JOB-14)를 돌리고, 키·IP 오류면 exit_only 주문만 멈추고 긴급 알림(MSG-E019, NTF-23)을 보낸다(D-068, TS-85). 선택하지 않은 코인과, 선택을 해제하며 [계속 보유]를 고른 보유분은 관리 대상이 아니다([매매 로직 명세](../03-functional/trading-logic.md) 11장). [계속 보유]를 고르면 손절이 멈춘다고 MSG-C007이 알리고, 기본 선택은 [손절·청산만 계속 관리]다(D-068 ④, 추적표 Q-09 해결).
- **증명:** 통합 TS-39. 속성: 임의 모드 전환 순서 → 전환 직전에 관리하던 실제 보유 코인이 전환 뒤에는 매도됐거나 JOB-02 대상(exit_only)이다.
- **관련:** TS-39, TS-85 · 5·9단계

### INV-11 대조가 끝나면 로컬과 거래소가 같다

- **정의:** 실제 자산 포지션(live, exit_only)의 선택 코인에 대해 (1) 잔고 대조(시작 점검 6번, 재연결·잠자기 복귀 뒤, JOB-14)를 마친 직후 로컬 보유 수량 = 거래소 `balance + locked`(무시 기준 안), (2) 주문 대조(같은 시점과 JOB-05)를 마친 직후 로컬의 끝나지 않은 주문 = 거래소의 `uat-` 미체결 주문이다. 단, D-046 확인 절차 중인 UNKNOWN 주문은 (2)의 비교에서 뺀다. 웹소켓이 놓친 체결은 `GET /v1/order`의 trades로 복구한다(D-070, TS-90). paper·live-validate 포지션은 거래소와 대조하지 않는다([매매 로직 명세](../03-functional/trading-logic.md) 11장).
- **깨지는 예:** 대조 중 들어온 myOrder 이벤트로 체결이 두 번 반영됨. 대조가 paper 포지션을 거래소 값으로 덮어씀.
- **증명:** 속성: 임의 차이(수량, 주문 누락·추가, 수동 주문) → 대조 → 같음. 통합: TS-09, TS-10, TS-70, TS-71.
- **관련:** TS-09, TS-10, TS-65, TS-70, TS-71, TS-90, TS-94 · 5·7단계

### INV-12 시세조종으로 오해받을 주문 패턴 없음

- **정의:** 하루(09:00 KST 기준) 주문 수 ≤ 일일 상한(정책상 예외인 손절 등은 따로 세어 기록), 같은 코인의 접수된 주문 사이 간격 ≥ 최소 주문 간격(접수되지 않은 주문은 세지 않음, D-061. 손절의 예외 여부는 Q-01), 걸었다 취소하는 주문의 반복 없음(취소 뒤 재주문은 위험 검사부터), 자기 주문끼리 체결 없음(INV-05·06).
- **증명:** 속성(상태 기계를 가짜 시계로 며칠 돌림): 주문 기록에서 간격과 개수를 센다. 통합: TS-31, TS-82, TS-114.
- **관련:** TS-13, TS-14, TS-31, TS-82, TS-114 · 5단계

### INV-13 요청 한도의 절반 이하, Origin 없음

- **정의:** 업비트 그룹별 1초 창의 요청 수가 한도의 절반 이하다([가짜 구현 명세](fakes-spec.md) 2.3절의 수). 웹소켓 연결·메시지도 절반 이하다. 모든 업비트 요청에 `Origin` 헤더가 없다. 429를 받으면 그 그룹을 다음 초 경계까지 멈추고, 418이면 차단 시간 동안 그 범위의 요청이 0건이다.
- **증명:** 속성: 여러 작업이 동시에 내는 임의 요청 폭주를 요청 한도 장치에 넣고 FakeClock으로 돌려 창별 수를 센다. FakeExchange 엄격 모드가 모든 통합 테스트에서 자동으로 검사한다.
- **관련:** TS-03, TS-05, TS-143 · 3단계

### INV-14 금액·수량은 Decimal

- **정의:** core의 금액·수량·가격 계산에 float가 없다. 업비트 응답의 숫자(문자열, JSON 숫자, 지수 표기)를 Decimal로 읽고, DB에는 지수 표기 없는 문자열로 저장하며(D-071), 다시 읽어도 같은 값이다. 위험 한도 비교는 반올림 전 Decimal로 하고, 정수 원 합계는 화면·알림·CSV 같은 보고에만 쓴다([데이터 모델](../04-data/data-model.md) 2장).
- **깨지는 예:** `json.loads` 기본값(float)으로 시세를 읽음. `Decimal(float값)`. 원화를 먼저 반올림한 값으로 한도를 비교해 1원을 넘김.
- **증명:** 속성: 임의 Decimal 문자열(뒤 0, 지수 표기, 긴 자릿수) → 파싱 → 저장 → 읽기 = 원래 값. 녹화 응답의 긴 자릿수(`acc_trade_price`) 단위 테스트. 구조 검사: core의 `float(` 사용 목록 고정.
- **관련:** TS-73, TS-102, TS-105 · 3·5단계

### INV-15 LLM의 실패·조작만으로 매수가 생기지 않음

- **정의:** LLM 응답이 무엇이든(형식 오류, 거절, 시간 초과, 429, 엉뚱한 내용, 인젝션을 따른 응답) 그것만으로는 매수가 생기지 않는다. 매수는 positive, 확신도 ≥ 임계값, 규칙 충족, 위험 통과가 모두 참일 때만이다. 응답 해석은 예외를 올리지 않고 검증된 시그널 또는 neutral을 돌려준다.
- **증명:** 속성: 임의 바이트·텍스트·JSON(스키마를 일부만 따르는 것 포함)을 응답으로 → 결과는 유효한 시그널이거나 neutral이고 예외가 없다. 통합: 지시를 따르는 FakeLLM(`obedient`) + 인젝션 뉴스 → 규칙·위험 조건을 못 맞추면 매수 0건(TS-20).
- **관련:** TS-18, TS-19, TS-20, TS-110 · 4·5단계

### INV-16 core는 시계를 Clock으로만 본다

- **정의:** core는 `time.time`, `time.monotonic`, `datetime.now`, `asyncio.sleep`, 이벤트 루프 시간을 직접 부르지 않는다. 주기는 monotonic 시간으로 재므로 PC 시계를 바꿔도 주기가 바뀌지 않는다. 날짜 경계(09:00 KST)는 거래소 시각(PC 시계 + 측정한 오차)으로 정한다. 그래서 PC 시계가 갑자기 바뀌면 다음 오차 측정(JOB-09, 1시간 이내)까지 날짜 경계가 어긋날 수 있고, 오차가 5초를 넘으면 그때 DEGRADED가 된다. 거래소 시각을 monotonic 시간과 마지막 `Date` 헤더로 계산할지는 결정 필요([추적표](traceability.md) Q-14).
- **증명:** 구조 검사(AST: core 아래 금지 호출 0건). 속성: FakeClock으로 PC 시계 오차와 점프를 임의로 넣어도 작업 실행 간격이 같고, 오차를 다시 잰 뒤의 일일 리셋 시각은 거래소 시각 09:00이다.
- **관련:** TS-42, TS-111 · 3·5단계

### INV-17 앱 인스턴스는 하나

- **정의:** 같은 사용자에서 앱 프로세스 두 개가 동시에 실행 잠금을 잡지 않는다. 두 번째 프로세스는 DB와 거래소에 아무것도 쓰지 않고 끝난다(두 프로세스가 같은 DB로 주문하면 중복 주문이 날 수 있다).
- **증명:** 통합(실제 프로세스 두 개, 리눅스에서 가능). 수동: [Windows 10 수동 점검표](manual-checklist-windows10.md) 6절.
- **관련:** TS-45, TS-135 · 6단계

### INV-18 기록이 빠지지 않는다

- **정의:** 앱이 만든 주문마다 결정 기록(reason_code)이 있다(재조정으로 들여온 주문은 출처를 reconcile로 표시). 주문 상태 변화마다 order_events가 있다. 시그널마다 입력·출력 원문과 응답 모델이 있다. 주문 기록은 전송보다 먼저다(INV-03). 체결 1건의 반영(fills, orders, positions, round_trips, daily_stats)은 한 트랜잭션이다(D-070, TS-91).
- **증명:** 속성: 상태 기계를 돌린 뒤 DB를 검사. 통합: TS-128.
- **관련:** TS-91, TS-128 · 4·5단계

### INV-19 모드마다 쓸 수 있는 주문 API가 정해져 있고 게이트를 건너뛰지 못함

- **정의:**
  - paper·signal-only: 매매 흐름에서 업비트 주문 생성·검증 API 호출 0건. signal-only는 가상 주문도 없다. 예외는 두 가지다. 실전 전환 화면(SCR-08)에서 사용자가 체크리스트 A의 "주문하기" 권한을 확인할 때의 주문 검증 호출(D-048 대기), 그리고 live → paper 뒤 남긴 exit_only 실보유분의 손절·청산 매도로 이것은 실제 주문(`/v1/orders`, identifier `uat-l-`)이다(D-068, TS-85).
  - live-validate: `/v1/orders/test`만 쓰고 `/v1/orders`는 0건.
  - live: `/v1/orders`.
  - live-validate는 인정일 28일 + 체크리스트 A 뒤에만, live는 live-validate 3일 + 매수 검증 오류 0건 + 체크리스트 B + 확인 문구 뒤에만 켜진다. 설정 파일을 고치거나 재시작해도 이 순서를 건너뛰지 못한다.
- **증명:** 통합: 모드별 FakeExchange 기록. 속성: 임의 모드 전환 시도 순서 → 허용된 전환만 일어난다. 화면: TS-120.
